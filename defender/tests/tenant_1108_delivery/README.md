### Choices where the amendment names behaviour, not a spelling

21. **Statuses** (*orchestrator ruling at review*, replacing this round's first reading). `finish(batch)`, `deliver(batch_id)` and `revert(lesson_path, lesson_name)` all return the same shape: an object with `.status` and `.url`.
    - `.status` compares equal to one of `"opened"` (a PR this call created), `"open"` (an open PR found, none created), `"merged"`, `"closed"` or `"nothing to deliver"`; a `StrEnum` works.
    - `.url` is the PR's URL for `opened` and `open`; otherwise it is not pinned.
    - Revert: a fresh revert answers `opened`, a revert whose PR is pending answers `open` with that PR, and a closed one refuses with `DeliveryRefused`, as before.
    - `nothing to deliver` means the branch's tip equals its base, or there is no branch. A batch with no commit has no branch (the first commit creates it), so `finish` answers `nothing to deliver`. A branch holding a foreign commit refuses instead (choice 34).
    - What `deliver` answers for an id with no branch is not pinned.
22. **Retries push nothing, also while the PR is open** (D-closed: "once the forge has had a PR for a batch (open, merged or closed), retries push nothing and open nothing"). The identity case's open row requires no batch branch on the remote.
23. **`TenantDelivery.open(..., network_timeout=<seconds>)`** is the wall timeout's one knob. The cases give 3 s and allow 15 s. *Orchestrator ruling (adversary M02):* the production default is finite. A stalled default cannot be waited out in a test, so it is pinned through an exported constant: `tenant_delivery.NETWORK_TIMEOUT`, a finite number of seconds above zero, and the delivery's `.network_timeout`, which is that constant when `open()` is given no `network_timeout` and the given value otherwise. The signature's default is not pinned.
24. **`BoxRequest.require_sandbox`** is the amendment's field name. The generic case builds one directly. Whether the drain's own request carries it, or `TenantDelivery.start_box` sets it, is not pinned; the drain's start through `start_box` is.
25. **`Batch.discard()`** removes the draft and keeps the branch. `Batch` has no `.worktree`.
26. **Temporary entries** are any name in `<T>/drafts/` with a leading dot (the amendment's `.<id>-<rand>`; the exact form is not pinned).
27. **The interrupt** is a `BaseException` subclass raised by a `SIGUSR1` handler in the main thread, sent when the stalled server meets the call. It is not `KeyboardInterrupt`, which would end the pytest session. An `Exception` may come out as `DeliveryRefused`; the interrupt must come out as itself.
28. **R7's probe.** Three identical `remote.origin.pushurl` values (two until adversary M09, a pipe preloaded with two copies): a push asks for the credential once per URL. Probed against the smart-HTTP fixture: clone, fetch (protocol 0 and 2), `ls-remote`, push (plain and `--atomic`), pull, `fetch --all` and `remote update` each ask once. An implementation that pushes to an explicit URL never asks again, so the case is vacuous for it, and so is the bug.
29. **R3's kill** is the building process's death by `SIGXFSZ` (a file-size cap, armed once the build begins under `drafts/`; `SIG_IGN` for the in-process failure). A build done by a subprocess would turn the kill into an in-process failure: the case then accepts that, and its sweep check has nothing to sweep. *Accepted false-red risk (review):* the draft lock audit (`test_the_draft_and_info_attributes_are_written_under_the_tenant_lock`) sees operations through Python's audit hooks, so it cannot see a rename made through `ctypes` (`renameat2`) or a sweep done by a subprocess (`rm`, `find -delete`); such an implementation fails that case for want of the probe point, though its lock may be right.
30. **The repository read** (`GET /repos/{o}/{r}`) at `open()` is required by the lock-free case (`("open", "repository")`), as the amendment places it.
31. **Hooks.** Network git runs no clone hook. Whether local git (the commit-maker's `update-ref`, the fast-forward) runs them is not pinned (*orchestrator ruling*), so choice 17's conditional hook case stands.
32. **A reused id.** Only "not answered with the old PR" is pinned. Whether the new batch's finish pushes and opens a PR, or refuses, is not. An implementation naming each batch's branch afresh passes vacuously.
33. **The fake answers at the clone's configured origin** (`configured_origin`, read with `git config`, before any `insteadOf`), so the smart-HTTP cases' forge is at `127.0.0.1:<port>`. The earlier cases' `ForgeHTTP()` default stays `forge.invalid:3000`.
34. **A branch holding a foreign commit refuses, even with no commit-maker commit past its base** (*orchestrator ruling at review*: amendment 3's "nothing to deliver" meant an empty branch). Provenance is checked before emptiness, and the refusal is loud: `DeliveryRefused`, nothing pushed, no PR. `nothing to deliver` is a branch whose tip equals its base, or none (choice 21). Three rows hold a branch whose only commits past its base are foreign:
    - `only-raw` and `amend` of `test_finish_refuses_a_branch_holding_a_commit_the_commit_maker_did_not_make` (a commit laid by plumbing on a branch the commit-maker never committed to; the commit-maker's commit amended away);
    - `amended` of `test_retained_branch_delivery_pushes_only_commit_maker_commits` (the retained branch's commit amended before a later delivery).

### Choices where the amendment was silent

1. **Locations.** Exports are exactly `<T>/exports/<commit>/` with the pointer `<T>/exports/current`; drafts are exactly `<T>/drafts/<batch>/agent`. The batch worktree is under the layout's `tenant.worktrees` (`<T>/learning/worktrees`): the amendment's `<T>/worktrees/<batch>` is read as the layout owner's worktree base (D7), not a new folder. *Accepted by the orchestrator at review.* Listings of `exports/` count folders and `current` only, so a lock or other file there is tolerated. *Amendment 3 (C2):* there is no batch worktree. Nothing may appear under the worktree base, and the draft is built in a temporary `<T>/drafts/.<id>-<rand>` (choice 26).
2. **`AgentChange.path`** is repo-relative POSIX (`agent/lessons/x.md`), like revert's lesson path and git pathspecs; `content` is `bytes`, or `None` for a deletion.
3. **Lanes** are declared once per batch, `start_batch(batch_id, lanes=...)`, and govern the box request, derivation and the commit-maker. Lane spellings are not validated by the contract: the amendment deletes the escape checks.
4. **Lock seam.** `tenant_lock(tenant)` is the production context manager the three locked steps use; a busy lock raises `LockBusy` (a `DeliveryRefused`) at once, naming the holder's pid. Probes run in another process, since same-process lock semantics differ by primitive.
5. **Revert (user decision, then orchestrator rulings, 2026-10-15).** A revert proceeds only while `main` still holds exactly what the commit-maker wrote for the lesson. The test is content, not history: the change a revert undoes is the most recent commit-maker change to the lesson whose resulting bytes equal `main`'s current bytes (so a human edit later restored to the agent's exact bytes proceeds, and an unmerged change, such as a later batch whose PR is still open or a failed earlier revert, never matches and is skipped without any merge detection); with no such change the revert refuses. It restores the bytes from just before that change, or deletes the lesson when that change created it, as one commit-maker commit on `main` with its own branch and PR. A human edit on `main` since, or a lesson the commit-maker never wrote, refuses with `DeliveryRefused`: nothing pushed, no PR, `main` unchanged. Other files changing on `main` do not stop it. Merge style must not matter: the agent's change is identified from the commit-maker's own commits, not by finding their shas on `main`. Cases: `test_revert_deletes_a_lesson_the_commit_maker_created` and `test_revert_restores_what_a_lesson_held_before_the_commit_maker_changed_it` (each merged by merge commit, squash and rebase), `test_revert_undoes_only_the_latest_of_several_commit_maker_changes` (changed once; changed back to the first bytes, where an earlier change matches too), `test_revert_ignores_a_later_commit_maker_change_whose_pr_is_still_open`, `test_revert_proceeds_when_main_again_holds_exactly_the_agents_bytes`, `test_revert_refuses_a_lesson_changed_on_main_since_the_commit_maker_wrote_it` (agent-created, agent-changed, a same-length edit, an edit appending to the agent's bytes), `test_revert_refuses_a_lesson_the_commit_maker_never_wrote` (the seed, a human-merged lesson), `test_revert_recreates_a_lesson_the_commit_maker_deleted` (orchestrator ruling: a merged commit-maker deletion follows the same rule, `main`'s absent lesson matching that change's result, so the revert recreates the bytes from before it). 19. **The draft is git's bytes, never a checkout's** (*orchestrator-confirmed*). 20. **No process started by a delivery call outlives the call** (*orchestrator-directed, after a CI flake*). That is the rule, and it is stricter than upkeep alone: the `/proc` check fails any process the call left running under the tenant's folders, upkeep or not, on purpose. Git's automatic upkeep is the case that prompted it, and the code's to turn off. Git >= 2.47 starts `maintenance run --auto` detached after a fetch, commit or merge. It takes `maintenance.lock` and writes (a commit-graph, a repack) after the git that started it has returned. Over the clone, that is a mutation no call makes and no lock covers: it outlives the call and races the next operation (O-F: "two drains ... fail on a git lock"). In the foreground it runs inside a fetch or commit the lock does not cover. So no call's git may run it over the clone (`test_no_git_upkeep_runs_over_the_clone_from_a_delivery_call`, after `open`, `publish`, `start_batch`, `commit`, `reset` and `finish`). *Amendment 3 (R8):* `test_network.py` holds network git to the same rule on a timeout, an exception and an interrupt.
    - **Seen by what it leaves, not by a trace.** The clone's own config forces a maintenance task that writes a commit-graph (`maintenance.commit-graph.enabled`, `.auto=-1`). Repository config reaches every git over the clone, whatever environment the code gives it. `GIT_TRACE2_EVENT` would miss a git run with a scrubbed environment (this author's scratch implementation drops every `GIT_*` variable), and the audit hook sees only this process's own spawns, never git's detached grandchild. A `/proc` scan adds what still runs at return: a process whose working folder, an open file or a path on its command line is under the tenant's folders (a git run with `--git-dir` from elsewhere is seen by the last two). An upkeep lock left in the clone fails too. A run that starts only after its call returned shows at the next call's check; after `finish`, the last call, the case polls 2 s for the graph.
    - **Positive controls.** A plain fetch with this process's environment, in a clone armed the same way, leaves the graph: nothing the suite sets turns upkeep off for the code under test. The scan sees a process by each of the three: one working in the clone, one holding a file there open from `/`, one naming the clone's `.git` on its command line from `/`.
    - **Not pinned:** how the code turns it off (`-c`, `GIT_CONFIG_*`). `gc.auto=0` alone does not (the detached run still starts); `maintenance.autoDetach=false` alone runs it in the foreground; `maintenance.auto=false` does.
    - **The fixtures' own git runs with upkeep off:** `no_upkeep` in `_git_env`, the planting hook and the smart-HTTP CGI; `BARE_NO_UPKEEP` (`receive.autogc` too) in each bare remote's own config, since local transport drops the pusher's `GIT_CONFIG_*` and receive-pack runs upkeep after every push. None of it reaches `os.environ`, `GitConfigHome` or `fresh_process_env`: those are the code under test's environment, and the later-process cases run its git there.

### Adversary round 2 repair (2026-10-16)

The adversary's second run on `0bb1fbd0` left one survivor. **R1** stages the export body in a temporary folder outside `exports/` with the lock released, taking the lock only for the fast-forward and for the rename into `exports/` plus the `current` swap. That greens the suite, and two interleaved publishers can move `current` back to an older commit. Adversary material read for this round: `round2/demos/test_zz_r2_repairs.py` only. The R1, KA and RE patches and `round2/base.patch` were applied blind to a scratch tree (`base.patch` onto this branch's pre-P3 production), never read.

- **Decision (flow 1, O-F).** The design holds the lock across the fast-forward, the export and `current` as one step, so a body write under a busy lock cannot happen at all. The paused publisher therefore neither refuses nor "merely avoids regressing": it holds the lock. The second publisher is the one that refuses (`LockBusy`, at once).
- **`test_two_publishers_never_interleave_so_current_never_goes_back`** folds in the adversary's interleaving demo, without seams.
  - A first publisher runs in another process. Its window runs from the end of its fast-forward (the older commit's marker checked out in the clone) to its write of `current`. The writes and spawns probed in that window:
    - every file it writes outside the clone, however opened;
    - every rename or link, with destinations relative to a folder descriptor resolved;
    - every program it starts.
  - Each of those is probed from a third process. All must see the lock busy, and the write of `current` must be among them.
  - At the first of those moments the publisher is paused. The remote then moves to a newer commit, and a second publisher must refuse with `LockBusy` without waiting.
  - The first publisher resumes and must publish the older commit whole. A later publish then publishes the newer one.
  - No spawn pattern is pinned, such as a per-blob `cat-file`. A program started inside the window is only one more moment that must find the lock held, so a `cat-file --batch` or in-memory exporter passes.
  - The case starts a lock probe per moment (at most 60), so it takes about 11 s on a small tenant and grows with the export. It also relies on the export following the clone's fast-forward, as the seams already state.
  - Pausing at that moment alone was not enough. My throwaway implementation's first moment after the fast-forward is a `git rev-parse` inside the lock, so an R1 variant of it stayed green until every moment was probed.
- **KA**: `current` written after the lock is released. Already killed by `test_the_export_and_current_are_written_under_the_tenant_lock`, and now by the interleaving case too.
- **RE**: the forge wraps only connection errors. Killed by six read-timeout and protocol cells of `test_a_transport_fault_is_a_forge_error`.
